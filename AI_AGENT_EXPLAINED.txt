===============================================================================
 PARALLAX - THE THREE-AGENT SUPPORT DESK, EXPLAINED SIMPLY
 Updated 25 August 2026
===============================================================================

This file explains, in plain language, how the customer support bot works.
No prior AI knowledge assumed.


-------------------------------------------------------------------------------
1. WHAT IT IS, IN ONE SENTENCE
-------------------------------------------------------------------------------

A customer asks a question. A "supervisor" works out whether it is a phone
problem or a computer problem, hands it to the right specialist, checks the
specialist's answer, and sends the final reply.


-------------------------------------------------------------------------------
2. WHAT IS AN "AGENT"?
-------------------------------------------------------------------------------

A normal AI chatbot only knows what it learned during training. Ask it "am I
still under warranty?" and it cannot know - it will either say so, or invent a
date that looks believable.

An AGENT is an AI that has been given a set of buttons it can press.

We call those buttons TOOLS. A tool is a small piece of ordinary Python code,
for example "go and look up this serial number".

The conversation really goes like this:

    Customer : "Am I still under warranty? Serial 5CD1234ABC"
    AI       : "I cannot know that. Please press check_warranty
                with serial_number = 5CD1234ABC."
    Our code : (presses the button)
               "Serial 5CD1234ABC: Dell XPS 15 9520, warranty ACTIVE
                until 14 March 2027..."
    AI       : "Yes, you are covered until 14 March 2027."

The AI never touches any system itself. It only ASKS for a tool to be run. Our
code decides whether to run it, runs it, and hands back the result.

That is the whole trick. Everything else is plumbing.


-------------------------------------------------------------------------------
3. WHY THREE AGENTS INSTEAD OF ONE?
-------------------------------------------------------------------------------

All three are the SAME AI model. What makes them different agents is:

  - a different set of instructions (its "system prompt"), and
  - a different set of buttons it is allowed to press.

That is genuinely what an agent is. Not different software - a different brief
and different capabilities.

  SUPERVISOR AGENT
      Sees every message. Decides who should handle it. Reads the specialist's
      draft and writes the final reply. Has NO tools of its own.

  MOBILE AGENT
      Phones, SIM cards, signal, tariffs, voicemail. Three tools.

  COMPUTER AGENT
      Laptops, desktops, drivers, hardware faults, warranty. Three tools.

IMPORTANT: the mobile agent physically CANNOT call the computer agent's tools.
Each holds its own separate toolbox. If routing ever goes wrong, the damage is
contained - the wrong specialist gives a useless answer rather than poking at
the wrong system.


-------------------------------------------------------------------------------
4. THE THREE STAGES
-------------------------------------------------------------------------------

Every message goes through the same three stages.

  STAGE 1 - ROUTE
      The supervisor is shown a description of each specialist and asked to
      reply with one word: mobile, computer, or none.

  STAGE 2 - DELEGATE
      The chosen specialist gets the message. It runs its own loop: think,
      press a button, read the result, think again, until it has an answer.
      That answer is called the DRAFT.

  STAGE 3 - REVIEW
      The supervisor is shown the customer's question, the draft, and what the
      tools actually returned. It writes the final reply.

If stage 1 answers "none" - the message is about neither phones nor computers -
stages 2 and 3 are skipped. The supervisor politely explains what the desk
covers. No specialist is bothered.


-------------------------------------------------------------------------------
5. HOW YOU USE IT
-------------------------------------------------------------------------------

Ask a question:

    POST http://localhost:8000/api/v1/support/ask
    Body: {"message": "am I still under warranty? serial 5CD1234ABC"}

See the setup:

    GET  http://localhost:8000/api/v1/support/agents

The easiest way is to open http://localhost:8000/docs in a browser. That page
is generated automatically - find the endpoint, click "Try it out", type your
message, press Execute. Much easier than typing curl commands on Windows.


-------------------------------------------------------------------------------
6. READING THE RESPONSE
-------------------------------------------------------------------------------

You get back the answer AND a record of how it was produced:

    answer     the final reply for the customer
    route      which specialist was chosen, and why
    delegate   the specialist's own draft, plus every button it pressed
               and exactly what came back
    review     whether the supervisor changed the draft
    stages     a plain list, e.g.
                 ["route -> computer",
                  "computer -> 1 tool call(s)",
                  "review -> final answer"]

This matters more than it looks. When an answer is wrong, you need to know
WHERE it went wrong:

  - wrong specialist chosen?        look at "route"
  - right specialist, bad lookup?   look at "delegate.steps"
  - good draft, mangled reply?      compare "delegate.answer" with "answer"

Without the trace you are just guessing.


-------------------------------------------------------------------------------
7. FOUR DESIGN RULES WORTH KNOWING
-------------------------------------------------------------------------------

RULE 1: Mistakes the AI can fix are handed back to it. Real breakages are not.

    If the AI asks for a button that does not exist, or sends nonsense
    arguments, we do NOT crash. We reply:
        "There is no tool named 'xyz'. Available tools are: ..."
    and let it try again. It usually corrects itself.

    But if the model server is down, we stop and report an error. Asking the
    AI to try again would be pointless.

RULE 2: Routing degrades instead of failing.

    Small models do not always answer with one clean word. If the reply cannot
    be read confidently, we fall back to simple keyword matching on the
    customer's message, and the response says so with "fallback_used": true,
    so you always know it happened.

    We are also careful about HOW we read the reply. A sentence like
    "this is not a computer issue, it is mobile" would be read backwards by a
    naive search for the first matching word. So the reply is only accepted if
    it starts with a label, or mentions exactly one label overall.

RULE 3: The review can never blank an answer.

    If the review step returns nothing at all, we send the specialist's draft
    unchanged rather than an empty reply.

RULE 4: There is a hard limit on tool rounds.

    Four by default. Without it, a confused model could keep pressing buttons
    forever.


-------------------------------------------------------------------------------
8. *** ABOUT YOUR MODEL: qwen2.5-coder:7b ***
-------------------------------------------------------------------------------

There is a real trap here, and you have already hit it once.

"Tool calling" is a specific skill a model has to be trained for. A model
without it will NOT show an error - it will quietly ignore the tools and answer
from imagination. Confident, well-written, completely invented.

Your model sits in a middle case. It DOES understand what to do: asked about a
warranty, it correctly decides to use check_warranty with the right serial
number. But it writes that decision as ordinary TEXT instead of putting it in
the proper slot the software reads.

So our code now also reads tool requests written as plain text and converts
them into real ones. It only does this when the name matches a tool we actually
offered, so a normal answer that happens to look like JSON is never mistaken
for a button press.

THE TELL: if "steps" comes back empty on a question that clearly needed a
lookup, the model is not really using its tools.

Verified working with qwen2.5-coder:7b on 25 August 2026.


-------------------------------------------------------------------------------
9. WHAT IS REAL AND WHAT IS FAKE
-------------------------------------------------------------------------------

REAL:
  - The three agents and their separate instructions.
  - The routing decision, made by the model.
  - The tool-calling loop.
  - The review step.
  - The whole HTTP surface.

FAKE:
  - The six tools return FIXED strings. check_warranty gives the same Dell
    XPS answer for any serial number you pass it. lookup_data_plan gives the
    same Unlimited 5G plan for any number.

That is deliberate. The purpose of this build is to prove the pipeline works
end to end. Wiring up a real CRM would not test anything the canned version
does not already test.

To make a tool real, replace the body of one function. Nothing else changes.


-------------------------------------------------------------------------------
10. WHAT WAS TESTED
-------------------------------------------------------------------------------

54 automated tests, all passing, no skips.

They need no model server and no internet: every AI reply is scripted. What is
being tested is the pipeline, not the model - routing (including the awkward
sentences), delegation, the separate toolboxes, recovery from bad tool calls,
the round limit, the review fallbacks, and the HTTP endpoints.

Separately, the whole thing was run for real against qwen2.5-coder:7b on this
machine. All three paths worked:

  "laptop crashing, serial 5CD1234ABC"    -> computer -> check_warranty
  "what data plan am I on? +4477..."      -> mobile   -> lookup_data_plan
  "book me a table for dinner"            -> none     -> polite decline


-------------------------------------------------------------------------------
11. WHAT COMES NEXT
-------------------------------------------------------------------------------

Natural next steps, roughly in order of usefulness:

  - Make one tool real, to prove the seam works with a live system.
  - Remember the conversation, so a customer can ask a follow-up question.
  - Let the supervisor send a draft back for another attempt when the review
    finds it inadequate, instead of only rewording it.
  - Add a third specialist (billing?) - it is a prompt and a toolbox, nothing
    structural.
